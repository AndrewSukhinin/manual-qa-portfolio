# Отчет по обучению: День 04

## 🧠 ЧАСТЬ 1: ЧТО ИЗУЧИЛ (Теория)

### 📑 1. Тестирование требований и статическое тестирование

Тестирование требований (статическое тестирование) — это процесс проверки проектной документации (ТЗ, макетов, пользовательских историй) до того, как разработчики напишут первую строчку кода. Главная цель — найти логические дыры, технические противоречия и нестыковки «на бумаге». Исправление багов на этапе текста обходится компании в десятки раз дешевле, чем на этапе готового кода.

#### 🔎 6 главных свойств «идеальных» требований (Чек-лист QA):

- **Полнота (Completeness)**: Требование содержит всю необходимую информацию для реализации и не оставляет вопросов.
- **Однозначность (Unambiguity)**: Текст сформулирован так, что у него есть только одно толкование. Избегаются слова-паразиты: «быстро», «красиво», «удобно» (это маркеры дефекта Ambiguity — двусмысленности).
- **Непротиворечивость (Consistency)**: Одно требование не должно противоречить другому внутри проекта.
- **Тестируемость (Testability)**: QA-инженер сразу понимает, какие конкретно шаги нужно воспроизвести, чтобы проверить выполнение требования. Если требование нельзя проверить объективно (нет четких метрик) — оно дефектно.
- **Ясность (Clarity)**: Текст написан простым, лаконичным языком, понятным и бизнесу, и разработке.
- **Актуальность (Up-to-date)**: Документация обновляется вовремя и соответствует текущему состоянию системы.

### 🔄 2. Анатомия User Story (Пользовательских историй)

В гибких методологиях (Scrum) вместо тяжелых и монолитных ТЗ требования оформляются в виде User Story — коротких формулировок технического требования, написанных на понятном человеческом языке от лица конечного пользователя. Каждая правильная User Story строится по жесткому шаблону:

> **Как** [Роль / Тип пользователя], **Я хочу** [Совершить какое-то действие / Получить функцию], **Чтобы** [Достичь определенной цели / Получить бизнес-ценность].

#### 📐 Чек-лист качества User Story (Критерии INVEST):

Чтобы Пользовательская История была качественной и готовой к разработке, она должна соответствовать стандарту INVEST:
- **I — Independent (Независимая)**: История может быть реализована и протестирована независимо от других задач.
- **N — Negotiable (Обсуждаемая)**: Это не жесткое монолитное ТЗ, а приглашение к диалогу между командой разработки и Product Owner.
- **V — Valuable (Ценная)**: Приносит понятную и измеримую бизнес-ценность пользователю или продукту.
- **E — Estimable (Оцениваемая)**: Команда разработки может оценить трудоемкость её реализации.
- **S — Small (Небольшая / Компактная)**: Объем задачи позволяет реализовать и протестировать её внутри одного спринта.
- **T — Testable (Тестируемая)**: Содержит четкие критерии приемки (Acceptance Criteria), по которым можно однозначно проверить результат.

### 🛠 3. Acceptance Criteria (Критерии приемки) и BDD-стиль

Сама по себе User Story слишком абстрактна. Чтобы очертить границы задачи, к ней пишутся Acceptance Criteria (Критерии приемки). Это условия, при которых задача считается успешно выполненной.
В современной разработке критерии приемки принято писать в строгом BDD-стиле (Behavior-Driven Development) с использованием синтаксиса языка Gherkin. Это делает сценарии понятными человеку и готовыми для автоматизации тестов.

#### 🛠️ Ключевые слова синтаксиса Gherkin:

- **Given (Дано / Контекст)**: Начальное состояние системы, предусловие (Pre-conditions).
- **When (Когда / Действие)**: Конкретное действие, которое совершает пользователь или система.
- **Then (Тогда / Результат)**: Ожидаемый результат (Expected Result) — что произошло после действия.
- **And / But (И / Но)**: Логические связки для объединения нескольких условий или результатов.

---

### 🔀 4. Обязательства Scrum-артефактов (Commitments)

У каждого из трех официальных артефактов Scrum есть ровно одно жесткое обязательство, которое гарантирует его прозрачность и качество:
- **Product Backlog** ➡️ **Обязательство: Product Goal (Цель продукта)** — долгосрочный стратегический ориентир для всей системы.
- **Sprint Backlog** ➡️ **Обязательство: Sprint Goal (Цель спринта)** — фокус и ценность текущей итерации.
- **Increment** ➡️ **Обязательство: Definition of Done (DoD / Критерии готовности)** — общий для команды чек-лист стандартов качества, без выполнения которого фичу категорически запрещено релизить на прод.

### 💻 2. Проектирование бэклога маркетплейса Allo.ua

Провел самостоятельную инженерную работу: декомпозировал бизнес-логику финтех-модуля «Купить в кредит / Оплата частями» на маркетплейсе Allo.ua и «восстановил» техническую документацию.
Сформировал в Jira 5 атомарных задач с типом **Story**, исключив автоматические «умные ссылки» (Smart Links) для сохранения чистоты и читаемости бэклога:

- **[SAM1-24] US-1: Динамический расчет «Оплаты частями» в карточке товара**
  - **Формулировка**: Как покупатель сайта Allo.ua, я хочу выбрать банк и количество платежей прямо в карточке товара, чтобы сразу увидеть сумму ежемесячного платежа до перехода в корзину.
  - **Критерии приемки (BDD)**:
    - **Given** Пользователь находится на карточке товара стоимостью 24 000 грн.
    - **When** Пользователь нажимает на кнопку «Купить в кредит».
    - **And** Выбирает вкладку «Monobank».
    - **And** Устанавливает ползунок количества месяцев на значение «6».
    - **Then** Система мгновенно пересчитывает сумму и отображает ежемесячный платеж: «4 000 грн/мес».

- **[SAM1-25] US-2: Блокировка рассрочки для дешевых товаров**
  - **Формулировка**: Как представитель бизнеса (Product Owner), я хочу, чтобы кнопка «Оплаты частями» блокировалась для товаров дешевле 500 грн, чтобы компания не несла операционные убытки на мелких чеках.
  - **Критерии приемки (BDD)**:
    - **Given** Пользователь открыл карточку чехла для телефона стоимостью 350 грн.
    - **When** Страница полностью загрузилась.
    - **Then** Блок покупки в рассрочку/кредит недоступен для взаимодействия.
    - **And** Отображается только стандартная кнопка «Купить».

- **[SAM1-26] US-3: Расчет итоговой стоимости для кредитов с комиссией**
  - **Формулировка**: Как покупатель, я хочу видеть изменение итоговой стоимости товара при выборе кредитных продуктов с процентной ставкой, чтобы прозрачно понимать сумму переплаты.
  - **Критерии приемки (BDD)**:
    - **Given** Пользователь открыл калькулятор кредитов в карточке товара стоимостью 10 000 грн.
    - **When** Пользователь переключается на вкладку «Мгновенная рассрочка (ПриватБанк)» на 10 месяцев (комиссия 2.9% в месяц).
    - **Then** Сумма ежемесячного платежа отображается с учетом процентов.
    - **And** Появляется строка «Итоговая стоимость: 12 900 грн» и «Переплата: 2 900 грн».

- **[SAM1-27] US-4: Сохранение настроек кредита при переходе в Корзину**
  - **Формулировка**: Как авторизованный пользователь, я хочу, чтобы при клике на «Оформить» в кредитном калькуляторе товар попадал в корзину с сохраненным выбором банка, чтобы мне не приходилось настраивать кредит заново при оформлении заказа.
  - **Критерии приемки (BDD)**:
    - **Given** Пользователь выбрал в калькуляторе «Оплату частями от А-Банк» на 4 платежа.
    - **When** Пользователь нажимает кнопку «Оформить рассрочку».
    - **Then** Открывается модальное окно Корзины.
    - **And** Возле товара отображается лейбл «Рассрочка: А-Банк (4 платежа)».
    - **And** Итоговая сумма к оплате на первом шаге оформления равна сумме первого взноса.

- **[SAM1-28] US-5: Обработка ошибки превышения кредитного лимита**
  - **Формулировка**: Как покупатель, оформляющий рассрочку, я хочу получить понятное предупреждение, если стоимость товара превышает мой лимит в банке, чтобы вовремя изменить условия или выбрать другой банк.
  - **Критерии приемки (BDD)**:
    - **Given** Пользователь оформляет покупку ноутбука за 45 000 грн в рассрочку Mono.
    - **When** Банк возвращает по API ответ об ошибке: «Недостаточно лимита на оплату частями».
    - **Then** Сайт Allo.ua не прерывает сессию заказа, а выводит поп-ап: «Сумма превышает ваш лимит. Вы можете оплатить часть суммы наличными, а остаток оформить в рассрочку».

## 📖 Глоссарий проекта (День 04)

- **Requirements Testing** — тестирование требований (анализ документации на логические ошибки до написания кода).
- **User Story** — пользовательская история (формат записи требований на человеческом языке от лица юзера).
- **INVEST** — чек-лист качества Пользовательской Истории (Independent, Negotiable, Valuable, Estimable, Small, Testable).
- **Acceptance Criteria (AC)** — критерии приемки (границы задачи и условия её успешного выполнения).
- **BDD (Behavior-Driven Development)** — разработка, основанная на поведении системы.
- **Gherkin** — человекочитаемый язык описания сценариев с использованием конструкции Given-When-Then.
- **Given / When / Then** — Дано (Контекст) / Когда (Действие) / То (Ожидаемый результат).
- **Ambiguity** — двусмысленность (дефект требований, когда у каждого участника команды свое понимание текста).
- **Product Goal** — Цель продукта (глобальное обязательство для Product Backlog).
- **Sprint Goal** — Цель спринта (обязательство для Sprint Backlog).
- **Definition of Done (DoD)** — Определение готовности (критерий качества и обязательство для Инкремента).
